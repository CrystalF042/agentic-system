`全部 109 项通过` 之后再扫一轮。**这一轮的数字应该会掉下来,那才是对的。**

## build93 那一轮:10 只票全部 SUFFICIENT,实质材料 4% → 57%

看起来是这一路修下来最漂亮的结果。但对着数字多看了两眼:

| | EDGAR 进闸门 | 实质 |
|---|---|---|
| NVDA | 8 | 6 |
| AMAT | 8 | 7 |
| QCOM | 8 | 7 |
| LRCX | 8 | 6 |
| MU | 7 | 5 |
| AMD | 7 | 4 |
| ARM | 7 | 8 |

**实质材料的条数基本就是公告的条数。** 而每只票都恰好是 8 条公告——
那是 `recent_limit: 8`。

于是我去看了 `fetch_edgar_recent` 的取数逻辑:

```python
for i in range(min(cfg["edgar"]["recent_limit"], len(forms))):
```

**它取的是"最近 8 份公告",和这些公告什么时候提交的完全无关。**
没有任何日期过滤。

一家公司只要历史上提交过 8 份文件,就永远能取到 8 份。所以:

> **从今往后,每只票每天都会拿到 8 份公告,闸门每天都会判「材料充分」。**

而这套闸门存在的全部理由,写在它自己的模块开头:

```
Unit A  evidence-triggered research —— 有新证据才重新研究
```

**它被拆掉了。** 一个六周前的 10-Q 不是今天的增量事实,但系统会天天把它
当成今天的证据端上来,然后每天启动一次多空辩论。这正是闸门当初要防的
"每日评论台"——而且没有一处报错,还伴随着一个看起来极其漂亮的指标。

---

## 改法:一部只收 7 天窗口内提交的公告

```
dossier / topic  → within_days=0   不筛,要的是公司近况全貌
证券一部          → within_days=7   只要"新发生的"
```

默认值是 0,所以 `dossier.py` 和 `topic.py` 的行为**一点没变**——
它们要的本来就是全貌,不是"今天有没有新事"。

7 天的依据:8-K 要求在事件发生后 4 个工作日内提交,一周足以覆盖;
又不至于把上个季度的 10-Q 当成今天的新闻。改的话是
`unit_a.EDGAR_WINDOW_DAYS` 一个常数。

筛掉几份会报出来——不报的话,"这家公司这周没动静"和"我们把它的公告
都筛掉了"在日志里长得一样:

```
EDGAR: ok（查到 8 份，7 天内 2 份（滤掉 6 份更早的），其中 2 份取到正文）
```

## 这一轮预期:数字会掉,而且**应该掉**

大多数公司一周内没有 8 份新公告——很多周一份都没有。所以合理预期是:

- 大部分票回到 THIN 或 INSUFFICIENT
- 只有这周真的发了 8-K / 10-Q 的票会到 SUFFICIENT
- 实质占比大概回到 10–25% 区间

**如果扫完还是 10 只全 SUFFICIENT,那说明这一周恰好是财报季**(有可能——
AMAT / LRCX / KLAC 都在 8 月底报季),或者窗口还是太宽。到时候把
`EDGAR_WINDOW_DAYS` 调到 3 再看。

## 这一轮的教训

前面几个 build 的缺陷都是"数字看起来正常,其实是错的"。这一个是反过来的:
**数字看起来好得反常,而它确实反常。**

4% → 57% 不可能来自一次接线。指标突然变得极好的时候,第一件事不是庆祝,
是去查是不是把衡量它的那把尺子改了——这次就是。
