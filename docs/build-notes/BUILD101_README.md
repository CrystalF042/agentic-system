build100 做到了预期：AMD 从 SUFFICIENT 掉到 THIN（2 条报道归并为 1 个事件，
那条 `Not a Revenue Windfall` 已剔除），KLAC 掉到 INSUFFICIENT。

KLAC 那边**标签质量**的变化最明显——上一轮 9 条清一色

（估值观点文 ×3、清单体、解读体、疑问式 ×2）。规则从这一刻起才是可审计的。

**ARM 从 2 掉到 1 不是回归。** 那条 `$2 Billion in Orders` 不是被判成别的档，
是**整条不见了**——它根本没进那 10 条材料。闸门没改主意，材料没了。

## 但这暴露了一个真缺陷

同一天，相隔 17 分钟的两跑：

```
17:13  ARM 实质 2
17:30  ARM 实质 1
```

**闸门有了它当初被造出来要消灭的那个性质。** 模块开头写着：
「同一批不变的数字，每天重跑 6 次，今天看多｜中、明天中性｜弱——
这不是市场在变，是采样噪声」。现在闸门自己就是这样。

原因在这里：

```python
pool = sorted(news, key=lambda n: n.score, reverse=True)[:MATERIAL_POOL]  # 先砍到 40
kept_pool = _prefilter(pool, info)                                        # 再判相关性
```

**先砍再筛。** 真机 ARM 那一跑：

```
去重 55 → 池 40（砍掉 15，没有任何人看过它们）→ 清洗 → 相关 10
```

活着进入清洗的那 40 条里，有 **30 条随即被判为不相关丢掉**了。
池子的 40 个名额，四分之三花在了马上就要扔掉的东西上；与此同时
15 条从未被检查过的材料被直接丢弃。

而进料行上一个字都没有：`pool` 这个数**存在 intake 字典里，
但从来没有被打印过**。55→40 这一刀是整条链路上最后一个纯盲区。

**这和 build91 修的是同一个缺陷**（"按相关性截断 → 才判实质度"），
只是在管道的另一端，我当时没看见它。

---

## 改法

```
旧：去重 → 按相关性砍到 40 → 清洗 → 相关 N → 补正文 → 排序 → 前 10
新：去重 → 清洗（全部）→ 相关 N → 池上限 40 → 补正文 → 排序 → 前 10
```

清洗是纯正则，跑 55 条和跑 40 条的代价差别可以忽略——**用它换掉
"没看过就扔"是笔很划算的买卖**。40 个名额现在全部给已确认相关的材料，
所以在 ARM 上这一刀根本不会触发（相关材料只有十几条），
它退回成一个真正的安全上限。

### 为什么这一刀仍然按相关性切，不按实质度

CAP 那一刀是**补完正文之后**才切的，所以可以实质优先。
池子这一刀在补正文**之前**——此时判定只能看标题，而 build91 修的正是
"标题含糊、事实在正文里"那一类：

```
标题        AMD in the spotlight this week            → 不实质
标题+正文   …completed the acquisition of ZT Systems  → 实质
            for $4.9 billion
```

按标题级实质度排序，恰好会把这类材料排到最后先砍掉，
**等于把 build91 的缺陷倒着重做一遍**。所以仍然按相关性切，
但必须报出来，并写明这些条目未经实质度判定：

```
→ 相关 58（符号消歧丢弃 16 条，占 22%） → 池上限 40（按相关性丢弃 18 条，**未经实质度判定**　⚠） → 前 10 条进闸门
```

盲砍可以，装作没砍不行。

---

## 这一轮你会看到什么

**符号消歧的丢弃数会涨。** 现在清洗跑在全部 55 条上而不是 40 条上，
被检查的材料多了，被消歧挡掉的自然也多。**那不是变严了，是原来有一批
根本没走到这一步。** 比例（62%）应该大致不变或略降。

**ARM 的相关材料会多几条。** 原来那 15 条没被检查过的里面，
按比例应该有两三条是相关的——`$2 Billion in Orders` 很可能就在里面。
如果它回来了，ARM 会回到实质 2。

**AMD 和 KLAC 今天不受影响**：它们去重后分别是 40 和 37 条，
本来就没到池上限，那一刀从来没在它们身上落下过。

## 变异测试

```
退回先砍再筛           MISS      intake 不写 pool_cut  MISS
进料行不报池截断         MISS      不写「未经实质度判定」   MISS
```

探针查的是 **AST**：`_prefilter` 的第一个实参不能是切片，
且 `MATERIAL_POOL` 出现的行必须在 `_prefilter` 调用之后。
不是查源码里有没有某串字符——那条教训这个仓库已经踩过七次。
