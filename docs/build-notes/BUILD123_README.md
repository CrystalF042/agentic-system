# 第一条：演习不算送到

这一版存在的理由，是一个我在写它的时候才发现的形状：

```python
deliver.send_text()  在 CIO_TG_DRYRUN=1 时  return True
```

也就是说**"演习"和"真发出去了"在返回值上长得一样。**
如果通知台账照着这个布尔值记"已通知"：

```
演习跑了一次 → 台账记「已通知」 → 以后不再推
→ 那条真正要你批的消息，一次都不会发出去
```

**而且没有任何一处报错。** 这正是这套系统一直在防的东西，
只是这次它藏在一个 `return True` 里。

所以推送这一层不用布尔值，用四态：

```
SENT          真的发出去了      → 记进台账
DRYRUN        有意不发（演习）  → **绝不记进台账**，也不点告警
UNCONFIGURED  没配 token/chat   → 不记，**点告警**
FAILED        发送失败          → 不记，**点告警**，下次重试
```

三个"没送到"的处理方式不同，但有一个共同点：
**都不能让台账以为这批已经通知过了。**

`DELIVERED = (SENT,)` 单独抽出来，有一条用例专门防止有人往里多加一个。

# 第二条：有意不发 ≠ 没送到

`UNCONFIGURED` / `FAILED` 点告警，`DRYRUN` 不点。

不分的话，每次演习都会点亮"提醒没送到"这盏灯——
**常亮的灯 = 不亮的灯**，真正没送到的那天它也会被忽略。

同一条规矩在 build121 是"被关掉的流水线和坏掉的流水线不许长得一样"。

# 第三条：不重复轰炸，但"没变化"不等于"不用管"

去重键是**内容指纹**，不是条数：

```
3 条换成另外 3 条 → 条数一样 → 按条数去重就一条都不推
                              而那 3 条是全新的决定
```

指纹取 `(提案号, 状态, 动作, Δ股数, 目标股数, 有效期)` 排序后哈希。
**Δ股数必须进指纹**——批准的是股数，同一只票股数变了就是另一个决定。

但"内容没变"有两种完全不同的原因：

```
刚推过，你还没来得及看      → 不用再推
挂了两个交易日没人动         → **必须再推，而且要说挂了多久**
```

后者是这套系统一直在防的形状：
**一条挂到过期自动作废的提案，和一条从来没产生过的提案，在结果上一模一样。**

所以有两条越过去重的路，每天最多各触发一次：

```
有条目挂了 ≥ 2 个交易日     ⏰ **已挂 3 个交易日**（措辞升级）
有条目明天就过期作废        ⚠ **还有 1 天就过期作废**
```

**挂多久按交易日算，不按自然日。** 周五提的、周一还没批是 1 个交易日不是 3 天；
按自然日算的话每个周末都会触发一次"挂太久"，那盏灯又废了。

# 第四条：0 条不发消息

每天推一条"今天没有要批的"就是一盏常亮的灯。

心跳里照样有 `pending 0`——**那是"今天跑过了"的证据**，
和"今天没有要批的"是两句不同的话，由两条不同的通道承载：

```
心跳      每天一条，全貌，包括全 0 的日子     ← research_run.py 推
待批提醒  只在内容变了 / 挂太久 / 上次没送到时  ← notify.py 推
```

# 第五条：按钮和命令行两条路都给

`run_tgbot.py` 没在跑的时候，点按钮的表现是**转一下圈然后什么都不发生**，
没有任何提示。所以消息里始终带命令行写法：

```
**1 条提案等你批准**　US_PAPER　2026-09-05

#1　AMD　BUY +21 股　0 → 21
    决策价 183.00
    目标 4.00%　合规 PARTIAL　有效至 2026-09-09

批准 = 固定这个整数股数，下一个交易日开盘成交它。

按钮需要控制台在跑（python run_tgbot.py）。没跑的话在电脑上：
  .venv/bin/python run_approve.py --approve <号>
  .venv/bin/python run_approve.py --reject <号> --reason "..."
```

按钮点下去调的是 `proposal_store.transition()`，和命令行**同一个函数**。

## 漏网的那条：我的变异被自己的实现绕开了

变异是「台账读不动 → 返回一个假的"已通知"状态」，返回值里
`fingerprint = "x"`。而真实的指纹是从内容算出来的，
**任何一个假值都和它不相等** → `changed = True` → 照样推。

也就是说这条变异**没有真的破坏行为**，它测不出我想测的东西。
（这和 build121 那条 `if False else 原样` 是同一类问题：
**一条抓不到的变异，和一条写错的测试是同一种东西。**）

改法两步：

一、**断言换个地方。** 从"结果推了"改成断 `state()` 本身：

```python
st = nt.state(PID)          # 台账是坏的
assert st["fingerprint"] == ""      # 读不动 = 从来没通知过
assert st["n_sent"] == 0
assert st["last_sent_day"] == ""
```

二、**补一条真的会沉默的变异**：「读不动就跳过这次提醒」。
那条一加进去，两套用例立刻都红。

17 条**两套各自都抓到**。

——**"从来没有"这四个字必须能印出来。** 一个从来没成功过的推送通道，
和一个昨天刚推过的，绝不能在报告上长得一样。

