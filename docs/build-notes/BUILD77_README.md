# build77 —— 第一次真机跑 CRO→PC 暴露的四个缺陷

这一版全部由 `run_pc.py` 的**第一次真实运行**驱动。四个缺陷里有一个是这套系统
最不能犯的错：**假否决**。

---

## 一、单位不符导致的假否决（最严重）

**现象**

```
CRO 否决 NVDA：已实现波动率(60日年化) 40.74 触及否决线 1.50
```

**每一个字都对，唯独单位错了。**

- `measures.ann_vol()` 返回**百分数**：`40.74` 表示 40.74%（源码里 `* 100`）
- `risk_officer.POLICY` 的阈值是**小数**：`veto_vol = 1.50` 表示 150%

于是 `40.74 > 1.50` 成立，NVDA 被当成"年化波动率 4074%"否决。
日志正常、理由行正常、报告正常——**只有结论是反的**。

这和你自己抓出来的 `Leverage = debt/assets` 是同一类：数据没错，是口径与解释对不上。
区别是这一次它直接决定了一只标的进不进组合。

**修法（三层，缺一不可）**

1. `measures.py` 顶部写死单位契约：`PERCENT_RETURNING` / `RATIO_RETURNING` +
   `as_ratio()` 换算函数。**契约写在产出数字的地方**，不写在使用它的地方。
2. `run_pc.py::_measures_for` 在边界上显式换算。Beta 与相关系数无量纲，不换算。
3. `risk_officer.check_units()` 在比阈值**之前**校量级：σ ∈ [0, 5]、
   回撤 ∈ [−1, 0]、Beta ∈ [−10, 10]。越界就**抛错**。

**为什么抛错而不是自动 /100。**
自动换算是在猜口径，猜错的方向同样静默——而且更难查，因为那时连一条报错都没有。
超出物理合理区间只可能是口径问题，把它变成一次必须处理的失败是唯一安全的处理。

口径不符的标的按**测量不可用**处理，**不落成否决**——否决会被读成真实风险判断。

**顺带**：否决与警戒理由改成百分号口径印，`render_one` 增加一行测量原值：

```
- 测量（小数口径）：σ60 40.74%　σ252 50.00%　Beta 1.90　近一年最大回撤 -20.21%
```

这一行本来就该有。有了它，`40.74% > 150%` 这种比较一眼就知道不成立。

## 二、`beta_corr` 返回三元组，被当成两元组解包

```
NVDA 的测量取不到：too many values to unpack (expected 2)
```

`measures.beta_corr()` 返回 `(beta, corr, n_aligned)`。真正的问题不在解包本身，
而在于**整段测量共用一个 `try`**：异常发生在 `beta_corr` 这一行，前面已经算出的
σ 和回撤留了下来、后面的全成 `None`，日志只说一句"测量取不到"。
**一次异常污染整组测量，而报告上看不出哪一项失败。**

现在每一项测量各自 `try`，基准行情也单独取（它只被 beta/corr 用到，
挂掉不该把 σ 和回撤一起清成 `None`）。`n_aligned` 一并带出，用来区分
"算不出"与"样本不够"。

---

## 三、被否决的标的一条 lineage 都没留

`run_pc.py` 在渲染循环里 `continue` 掉了 `pc_ledger.record`，于是：

```
lineage 记录 1 条，其中 CRO 否决 0 条        ← NVDA 明明被否决了
```

**一个正常显示的、错误的统计量。** 而"哪些票被风险层挡掉了"恰恰是这张表最该
回答的问题——不落库，风险层对历史收益的影响就永远不可复盘。

现在否决行、无仓位行、口径不符行全部落库。`--stats` 增加"无仓位 N 条"与
按原因分组。自检用 AST 断言渲染循环里没有任何 `continue`（不 grep 文本：
解释这个缺陷的注释里本身就有 "continue" 这个词）。

## 四、3 只票 6 行持仓

`summary()` 只按 portfolio 分组，两个账户各持同样三只票就显示成
"6 笔：688012、002371、300308、688012、002371、300308"，读起来像台账重复。

**同票多账户与台账重复必须分开**，因为处理方式完全相反：一个绝不能去重，
一个必须去重。现在 `summary()` 按 (portfolio, account) 拆开，新增
`duplicates()` 按 (portfolio, account, code) 检出真正的重复行并在报告里告警。

跑完看一眼输出的账户拆分，就知道你这 6 行属于哪一种。

---

## 五、自检不再污染真实 cio.db

build76 的自检直接往 `cio.db` 写 `TESTPC` 假 lineage 行。
**pc_lineage 是归因分析的唯一依据**，假行和真行长得一模一样。
build77 起自检写临时库；历史遗留用 `scripts/purge_test_lineage.py` 清理
（先预览，加 `--apply` 才真删）。
