# 一、然后是 114 交付里那处自相矛盾

你那份输出上下两行是打架的：

```
成对基准对称，两个基准都正常                                   ← 判据说没事
**基准最后一根收盘是 NaN** —— 会让全市场的大盘超额同时变 null   ← 警告说要出事
```

**第二句在修完之后是假的。** 那根 NaN 现在会被 `align()` 丢掉、超额照算。
它描述的是**修复之前**的后果。

而 yfinance 那根未落定的尾行**每天都会有**——也就是说这盏灯从今往后
天天亮，报一个不会发生的故障。

> **常亮的灯和不亮的灯是同一种缺陷。**

这句话是我自己在这一轮变异测试里写下来的
（`if not st.get(...)` 那条探针的注释：*"常亮的灯等于没有灯"*），
然后转手就发了一盏。

## 为什么会这样

我先写警告，后写修复。警告的措辞停在了写它的那一刻，
而修复改变了世界。**没有任何东西会因为"修好了"就去回头改警告的文案。**

新的措辞说的是现在：

```
基准最后一根收盘是 NaN（yfinance 未落定的尾行，常见）—— **已按不可用样本丢掉**，
超额照算；代价是这一路的超额截止到上一个交易日，比板块那一路晚一天
```

有一条用例钉住它**不许再出现"变 null"这种字样**。

# 二、那个真实的代价：两个基准的截止日不是同一天

这才是尾行 NaN 现在唯一的后果，而 114 里它是**完全看不见的**：

```
SPY 尾行不可用 → 那一天整对被丢掉 → 大盘超额截止到 T-1
板块 ETF 正常   →                  → 板块超额截止到 T
```

**两个数进的是同一个 `relative_strength` 家族分，as-of 却差一天。**
不大，但正是不该沉默的那一类——它每天发生，而且从分数上完全看不出来。

现在卡片上多两个字段，扫描里多一段：

```
rs_mkt_as_of / rs_sector_as_of

  **两个基准的截止日不一样** —— 超额进的是同一个家族分，as-of 却不同：
    大盘截止 2026-09-03　板块截止 2026-09-04　502 张卡片
```

# 三、`1255 行（要 400 行）` 是措辞错，不是数错

`_yf_period()` 把 400 个交易日映射成 yfinance 的 `5y` 档——刻意的，
因为 `{n}d` 会被当**自然日**解释、少给约 30% 的 K 线。所以拿到 1255 行是对的。

但"要 400 行"这个说法会让人以为出错了。改成：

```
基准面板：yfinance:SPY(adjusted)　1255 行（至少要 400 行，够）　2021-09-07 … 2026-09-04
```

# 五、你那份扫描里还有一个数值得说一句

```
20.5%  price_structure.atr_to_nearest_zone_above　（103/502）
```

**这不是数据缺口，是一个结构事实**：这 103 只票**上方没有价区**——
多半是在创新高、头顶没有成交密集区。

而 setup 的 C 条件是"距上方价区 ≤ 0.5 ATR"，`dist is None` 判 False。
也就是说：

> **正在创新高的票，按构造永远通不过这个 setup。**

对这个 setup 来说这是**对的**（它整个就是在描述"逼近上方套牢盘"这件事），
但它是**结构性排除，不是偶然缺数据**——排除掉的是全市场五分之一。
`evaluate()` 已经把它记进 `unknown` 了，我只是把这件事讲明白，
免得以后有人看到 20.5% 以为是数据问题去"修"它。

**这一条我没有改任何代码，只是说清楚。**
